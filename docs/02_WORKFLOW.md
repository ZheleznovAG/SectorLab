# Инженерный процесс SectorLab

## Принятая комбинация подходов

- **Инкрементальная разработка:** добавлять возможности маленькими законченными частями.
- **Итеративная разработка:** возвращаться к уже работающей механике и улучшать её по обратной связи.
- **Vertical Slice (вертикальный срез):** проходить одну возможность от действия игрока до результата, а не писать всю инфраструктуру слоями.
- **Walking Skeleton (работающий каркас):** рано проверять минимальный путь «Unity → сборка → ввод → реакция».
- **Kanban + WIP=1:** только одна активная микро-задача.
- **Практики XP:** маленькие изменения, регулярные проверки, рефакторинг, частая интеграция, выборочный TDD.
- **Эволюционная архитектура + KISS/YAGNI:** не строить абстракции под неподтверждённые требования.
- **Геймдизайн через гипотезы и MDA:** оцениваем не наличие механики, а поведение и ощущения игрока.
- **Осознанная практика:** пользователь выполняет действия своими руками и объясняет решения.

Ни один из этих терминов не является оправданием тяжёлого процесса с огромной документацией. Полноценный Scrum для одиночной работы не нужен.

## Цикл одной микроитерации

1. **Цель:** одно измеримое изменение (например, появился Plane).
2. **Минимальная теория:** только понятия, нужные сейчас (например, Transform.position и Transform.localScale).
3. **Ручная реализация:** действия в Unity или небольшой участок кода.
4. **Проверка:** открыть/запустить, проверить ожидаемое поведение и один крайний случай.
5. **Осмысление:** почему это работает, ограничения, другие варианты.
6. **Коммит:** небольшая логическая фиксация после проверки; не переписывать историю.
7. **Обновление журнала (при полезности):** чему научились, замеченные риски, следующий шаг.

**Один этап R0.x может содержать дополнительные R0.x.y, если пользователь хочет мельче.** Коммиты привязаны к осмысленным завершённым изменениям, а не к числу кликов.

## Формат короткой задачи

- **Контекст:** текущее проверенное состояние.
- **Цель и нецели:** что меняем и что пока не трогаем.
- **Действия:** 3–7 шагов или небольшой код, без разворачивания будущей архитектуры.
- **Критерии готовности:** чётко наблюдаемые результаты.
- **Вопрос на понимание:** один, при необходимости.
- **Коммит:** `type: short description` после подтверждённой проверки.

Шаблон: [`templates/MICRO_TASK.md`](templates/MICRO_TASK.md).

## Роли

| Пользователь | Агент |
| --- | --- |
| Создаёт объекты/пишет код/меняет настройки | Объясняет, предлагает минимальный вариант |
| Запускает Unity, проверяет сцену и Android | Помогает сформировать проверку и разобрать ошибки |
| Принимает архитектурные решения | Сравнивает варианты, показывает компромиссы |
| Делает коммиты и выбирает темп | Предлагает границы коммита, проводит ревью |

При явно запрошенном автономном изменении агент может редактировать ограниченный набор файлов, но сначала смотрит статус проекта, описывает затронутые файлы и не делает соседние задачи.

## Обратная связь

После каждого крупного R0/R1/... — короткое ревью: что работает, что не работает, чему научились, что оказалось лишним. После R3 — регулярные игровые тесты (не только технические).
