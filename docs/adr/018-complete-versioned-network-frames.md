# ADR-018 — Полные снимки и граница сетевого матча

**Дата:** 2026-10-26  
**Статус:** принято

## Контекст и проблема

Два независимых сообщения MatchState/Units использовали один unreliable sequenced pipeline.
При перестановке пакетов более поздняя половина могла вытеснить раннюю, оставив клиент со смесью
состояний. Команда содержала только номер слота: очередь предыдущего матча или предыдущего
воплощения бойца могла управлять новым. Успех отправки не проверялся.

## Варианты

- Разные каналы для половин: устраняет взаимное вытеснение, сохраняет частично обновлённый кадр.
- Полный снимок с границей матча: немного больше повторяемых данных, простая проверка целостности.
- Полная репликация движка: лишняя сложность для шести бойцов и локальной сети.

## Решение

Протокол v2. Надёжные Begin/Ready согласуют поколение матча и отпечаток локальной конфигурации
после загрузки префабов. Отпечаток включает версию игры, правила, состав, характеристики,
позиции появления и параметры узлов. Хост не снимает WaitingForPeer до Ready; клиент не принимает
приказы до первого полного кадра. Несовместимость и тайм-аут объясняются с выходом в игру с ИИ.

Единственное ненадёжное сообщение — полный FrameSnapshot: поколение матча, номер снимка,
номер игрового тика, игровое время, очки/узлы и все слоты UnitView. Пауза останавливает игровой тик,
но heartbeat получает новый номер снимка. Шесть слотов и три узла занимают 229 байт с типом сообщения.
Поколение бойца, состояние жизни, HP/maxHP, время возрождения и счётчик выстрелов едут вместе.

Все поля проверяются до изменения модели. Поздняя ошибка и повторный ID не меняют даже первую
запись. Старые/повторные снимки отбрасываются; сообщения другого матча не запускают симуляцию.
Команда содержит поколение матча и поколения исполнителя/цели; хост проверяет их перед Execute
и по-прежнему подставляет команду игрока, назначенную соединению.

IMessageChannel.Send возвращает результат постановки в очередь. UtpChannel проверяет размер,
BeginSend и EndSend; ClientCommandSink подтверждает приказ только при Queued. Это подтверждение
отправки, не подтверждение выполнения хостом. Потерянные приказы после отключения не буферизуются.
ClientUnitView владеет визуальными прокси отдельно от координации сеанса.

## Последствия

Протокол несовместим с v1: оба участника используют одну сборку. Объём мал для Wi-Fi,
дельта-кодирование не требуется. Отпечаток обнаруживает несовпадение настроек, не служит
аутентификацией. NetworkLaunch хранит счётчик матчей только на время соединения;
одна активная симуляция на процесс остаётся ограничением проекта.

## Проверка

NetworkFrameTests: повреждение последнего слота, дубликат ID, потеря/перестановка/повтор кадров,
несовместимость, отсутствие синхронизации и заполненная очередь. NetworkSessionTests:
приказ в очереди при смене матча и возрождении бойца. NetworkMatchTests/ClientPresentationTests:
реальные UI и сцена. UtpChannelTests: согласование и игра через UDP localhost.
Итоги прогонов фиксируются отдельно в STATUS и evidence.
