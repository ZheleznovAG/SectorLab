## Варианты облачного Unity

**GameCI остаётся подготовленным вариантом.** Текущий workflow ожидает содержимое `.ulf`,
Unity email и пароль. [GameCI описывает получение файла через Hub](https://game.ci/docs/github/activation/),
но сам предупреждает, что наличие лицензии в Hub ещё не означает наличие `.ulf`.
Для Unity Personal [ручная активация через `.alf` официально не поддерживается](https://docs.unity.com/en-us/engine/6000.6/manual/get-started/install-and-upgrade/licenses-and-activation/manual-license-activation/manual-activation-guide).
Это разные способы активации: успех в Hub и заполненные secrets не доказывают успешную активацию
контейнера. Пустые значения, отключение preflight или покупка Pro без проверки не закрывают R-03.

**Unity Build Automation подходит для ограниченного пилота.** [Официальная документация](https://docs.unity.com/en-us/build-automation/reference/unit-tests)
подтверждает EditMode/PlayMode, падение сборки при упавшем тесте и выгрузку отчётов. Тесты выполняются
как часть build target; это не обещание отдельного бесплатного test-only runner.

Доступность **6000.6.4f1** пока **не подтверждена**. [Таблица поддерживаемых версий UBA](https://docs.unity.com/en-us/build-automation/reference/supported-unity-versions)
не перечисляет конкретную версию проекта. Отсутствие строки в этой общей таблице не доказывает,
что Editor недоступен: требуется проверка селектора версий или авторизованного API в выбранной организации.
Подменять версию проекта ради пилота пока не нужно.

[Unity публикует бесплатные месячные лимиты](https://unity.com/products/pricing-updates): 200 Windows Micro,
100 Linux Micro и 100 Mac Standard минут. Реальный остаток организации, доступные машины и расход
первого импорта проверяются в Dashboard до запуска. Платный тариф и платёжный метод не подключались.

Домашний Windows runner в публичном репозитории сейчас не предлагается: это выполнение кода PR
на постоянной машине; [GitHub отдельно описывает риск](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners).

## Пилот UBA небольшими шагами

1. Выбрать Unity Cloud organization/project и связать его с SectorLab. Убедиться в доступности
   **точной** версии `6000.6.4f1`, выбранной Windows-машины и квоты. Если версия недоступна,
   зафиксировать результат и продолжить проверку поддерживаемой активации GameCI.
2. Создать одну пробную конфигурацию для Windows, корень проекта — корень репозитория,
   исходники — конкретный commit SHA. Включить получение настоящих LFS-файлов. Запуск Android APK
   на каждый PR не требуется.
3. В Advanced Settings → Tests включить EditMode, PlayMode и **Mark build as failed if any test fails**.
   Проверить, что выполняются собственные тестовые сборки, а не только посторонние package tests.
   В отчётах ожидаются **88 + 172**, ноль failed/skipped/inconclusive. Другие числа требуют разбора,
   а не автоматического признания новой базы зелёной.
4. Сохранить source SHA, версию Editor, build/test reports, длительность и расход минут.
   Сверить облачные результаты с локальными. Отдельно контролировать упаковку Addressables:
   успешные тесты в Editor не заменяют проверку файлов Player.
5. Проверить передачу результата в GitHub. Нужен check/commit status на **том же SHA**, который
   проверялся, с понятным именем и ссылкой на отчёт. Уведомление о сборке в Dashboard само по себе
   не блокирует PR. Нативная интеграция статусов для SectorLab ещё не проверена; новый API-мост
   следует писать только после подтверждения, что его действительно не хватает.
6. После первого зелёного прогона включить обязательные быстрые checks и выбранный Unity check
   в правилах `main`. Проверить запрет слияния при failure, отсутствии/ожидании результата и отмене.
   Учесть, как владелец будет отправлять будущие изменения через PR.
7. В отдельном пробном PR намеренно изменить assertion существующего теста: облачный Unity check
   должен стать красным, слияние — недоступным. Исправить assertion новым коммитом, получить зелёный
   результат и разрешённое слияние. Не сливать заведомо сломанный вариант и не переписывать историю.

Если для интеграции понадобится API, [текущая документация UBA](https://docs.unity.com/en-us/oas-build-automation-client/3.0.0)
разделяет v3 для проектов/SCM и v2 для builds/targets. Она использует service-account key/secret;
старые примеры с legacy API key нельзя переносить без проверки. Создание ключей и подключение
GitHub-доступа выполняются отдельно от чтения репозитория; значения в Git и отчёты не попадают.

## Частота и критерий готовности

- Быстрый CI остаётся на каждом PR. Unity проверяет изменения игровых исходников, ассетов,
  пакетов и значимых настроек до слияния. Android packaging/device acceptance — отдельный рубеж.
- Пока облачный путь не подтверждён, текущие триггеры не менялись. После пилота можно исключить
  чисто документальные изменения, сохранив всегда публикуемый итоговый gate: простой top-level
  `paths` filter для required workflow может [оставить check в Pending](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging).
- CI завершён, когда один и тот же PR демонстрирует **красный тест → запрет merge → исправление →
  зелёный тест → разрешённый merge**, а результат привязан к актуальному SHA. Число проверок в
  старом архиве или зелёная карточка отдельной сборки такого подтверждения не дают.

## Сопутствующее замечание bootstrap

`NetworkMatchBootstrap` ищет зависимости при запуске, готовности и редких событиях UI/сети.
В его `Update`/`LateUpdate` поиска компонентов нет. Это небольшой долг явной композиции,
а не измеренный кадровый bottleneck. При следующем изменении bootstrap можно сохранить ссылки
на HUD/result/audio рядом с уже сохранёнными battle/lifecycle/commander. Новый DI-слой и
архитектурная переработка для этого не требуются; сейчас игровой код не менялся.
