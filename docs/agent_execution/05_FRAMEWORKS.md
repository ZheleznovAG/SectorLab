# 05. Реальное применение VContainer, UniTask, Addressables

Все три требуются для v1.0 не ради «галочки», а для конкретной цепочки **спавн/возрождение юнитов → матч → выход/Restart**. Версии пакетов должны быть закреплены в manifest и lock и проверены в Unity проекта. Сначала компиляция после установки каждого пакета, потом изолированная функция и тест.

## VContainer: что сделать

- Установить пакет в версию с проверенной совместимостью с Unity проекта (UPM через официальный репозиторий). Записать источник, точный tag/commit и лицензию.
- Создать **один** `GameLifetimeScope`, который собирает зависимости текущей игровой сцены. Использовать конструкторное внедрение для чистых сервисов, поддерживаемую инъекцию Unity-компонентов в разумном количестве.
- Реальные получатели: `MatchCoordinator`/`MatchClock`, `UnitFactory`, `EnemyTacticsController` либо интерфейсы им эквивалентные. Точность API проверять в установленной версии.
- Проверить один экземпляр match-scope сервиса в рамках матча и отсутствие выжившего сервиса после перезагрузки. Не использовать `Resolve` внутри произвольного `Update`.

## UniTask: что сделать

- Закрепить версию UniTask из официального Cysharp проекта; использовать в жизненном цикле юнитов как `UniTask<T>`/`UniTask`, а не декор вокруг синхронного метода.
- `SpawnUnitAsync`/`RespawnUnitAsync` связывает запрос загрузки prefab, ожидание, создание экземпляра, регистрацию и отмену. Покрыть Restart, смерть, выход и ошибку загрузки.
- Не полагаться на то, что `CancellationToken` автоматически останавливает нижележащую Addressables-операцию; корректно обрабатывать поздний `handle.Result` и гарантировать release.
- Сравнить с `UnityEngine.Awaitable` в коротком ADR, объяснить выбранную причину (совместимость со стеком, удобство отмены/средств для тестирования), не представлять UniTask как обязательный для всех операций Unity.
- Никаких необработанных исключений `async void`; если `Forget`, то с контролируемой обработкой ошибок и bounded lifetime.

## Addressables: что сделать

- Установить совместимую версию через Unity Package Manager. В документации для Unity 6000.6 доступны `2.11.2` и более новые major-ветки; **агент проверяет подходящий package и API в конкретном Editor**, не повышает major бесконтрольно.
- Для первого вертикального среза использовать **локально встроенный** Addressable prefab одной роли. Проверить режим PlayMode и построенный Player с **реально собранным content**.
- Перевести фактическое создание/возрождение всех 3 ролей на единый provider/factory с адресуемыми prefab или типизированными AssetReference, не оставляя неработающий учебный код.
- Убедиться, что Group/labels/ключи разумны, asset-зависимости не дублируются без причины, и билд содержит локальный контент. Удалённые CDN/Remote Catalog **не нужны**.
- Освобождать каждый handle или экземпляр строго по выбранной модели владения; отслеживать инвалидные/повторные release, stale references и перезапуски.

## Отдельные проверяемые сценарии

1. Один юнит создан из Addressable prefab после запроса через службу, связанную VContainer, при управлении временем через UniTask.
2. Три роли по обеим сторонам появляются/погибают/возрождаются и работают с NavMesh.
3. Отмена загрузки при Restart не порождает «призрачных» юнитов.
4. Ошибка ключа Addressables не приводит к зависанию партии и имеет понятную обработку для игрока.
5. Десять последовательных матчей не повышают число оставшихся активных экземпляров/handle/подписок после закрытия предыдущих матчей.
6. Все три библиотеки указаны в README с конкретными местами применения и тестами.
