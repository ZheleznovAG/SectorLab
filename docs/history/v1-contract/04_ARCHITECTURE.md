# 04. Целевая архитектура: минимальная, проверяемая, без псевдопромышленного каркаса

## Принцип

**Сохранять рабочую структуру** (`Units/`, `Player/`, `Battle/`, `Health`, `UnitStats`, `NavMeshAgent`); вводить новые компоненты вокруг реальных задач. Цель — ясные зависимости, разделение игровых правил и Unity-инфраструктуры, безопасный жизненный цикл загрузок и матчей. Один Unity-проект, без собственного движка.

## Слои и зоны ответственности

```
UI / PlayerInput / CameraController     EnemyAI
           |                               |
           +---------- Orders -------------+
                          |
                    MatchCoordinator  <---  MatchRules / Score / Clock
                          |
              Unit / Capture / Combat
                          |
             UnitFactory / UnitLifecycle
                          |
      AddressablesAdapter / Cancellation
                          |
              Unity NavMesh, GameObjects

Composition Root: VContainer LifetimeScope (связывает зависимости, но не подменяет логику)
```

**Переход с текущего кода:**
- `UnitCommander` оставить точкой интеграции пользовательских действий; при расширении input выделить `PointerGestureInterpreter` для tap/pan/pinch и экранные препятствия.
- `UnitMovement` и `UnitAttack` оставить ответственными за исполнение движения/атаки; ИИ и игрок должны отдавать команды через один понятный API. Не требовать интерфейсов для каждого `MonoBehaviour` без реального тестируемого смысла.
- `Health` дополнить `Heal` с тестами; не превращать чистую модель в `MonoBehaviour`.
- `BattleRules`/`BattleController` мигрировать к `MatchState` + `MatchRules` для победы по очкам/времени. Избегать двух параллельных неконсистентных условий завершения.
- Добавить `RelayRules` (чистые вычисления владения/захвата), `RelayPoint` (связь мира и правил), `ScoreService`/`MatchClock` (без MonoBehaviour там, где это просто вычисления).
- Добавить `EnemyTacticsController` с простым детерминированным назначением задач и переоценкой при изменении ситуации; без Behavior Tree или ML.

## Composition Root и время жизни

- **VContainer `GameLifetimeScope`** размещается в игровой сцене; регистрирует одну игру/матч, сервис часов, состояние матча, фабрику юнитов, управление ресурсами. Компоненты сцены могут быть зарегистрированы существующими instance-объектами, где это обоснованно. Не держать все объекты `Singleton` между рестартами.
- Ограничить контейнер границами composition root и bootstrap. Произвольные скрипты не должны через Service Locator вытягивать глобальные зависимости.
- `MatchScope`/контроллер матча владеет `CancellationTokenSource` или связанным токеном времени жизни объекта/сцены. Любая загрузка/спавн знает, как завершиться после отмены.
- Явные события (например, `OnUnitDied`, `OnRelayCaptured`, `OnMatchFinished`) с корректной отпиской; избегать глобального EventBus.

## Правила как чистые вычисления

- Владение/скорость захвата, начисление очков, время, победа/поражение/ничья, заживление и ИИ-приоритеты по возможности выражаются в чистых C# классах. Unity-компоненты снабжают модели состоянием мира и отображают результат.
- Временная дискретизация должна быть определена и одинакова для Editor/Android; в тестах используется контролируемый clock/tick, а не `WaitForSeconds` для проверки чисел.
- `UnitStats` и `RelayConfig` — ScriptableObject для настраиваемых данных; никаких копий числовых характеристик в EnemyAI.

## Ресурсы: единственный владелец

- `IUnitPrefabProvider` / `UnitFactory` в небольшом количестве обоснованных абстракций: загрузить prefab через Addressables, создать экземпляр, отдать владельцу, при смерти/рестарте освободить правильно. Выбрать одну модель владения: `Addressables.InstantiateAsync` + `ReleaseInstance` **либо** `LoadAssetAsync` + `Object.Instantiate` + общий handle до смерти последнего клона. Не смешивать схемы.
- Хранить связь spawned unit ↔ handle/ownership; отсутствие экземпляра после ошибки/отмены — нормальное управляемое состояние.
- Обязательно тестировать **отмену во время загрузки**, когда асинхронная операция может физически завершиться позже отменённой логической задачи: поздний результат нельзя допустить в уничтоженную сцену, нужно корректно освободить ресурсы.
- Тестировать, что при `Restart` нет двойного destroy/ReleaseInstance и не сохраняются `Unit.All` ссылки от прежнего матча.

## Проектные границы и дерево директорий

```
Assets/_Project/
  Scenes/Main.unity               # игровой сценарий; исходную сцену не стирать вслепую
  Scripts/
    Battle/                       # правила и жизненный цикл матча
    Units/                        # существующая логика юнитов
    Player/                       # ввод, камера, выдача приказов
    Objectives/                   # узлы захвата и начисление
    AI/                           # противник
    Infrastructure/               # DI bootstrap, Addressables, async
    UI/                           # HUD, обучение, пауза, итоги
  Data/Units/                     # существующие ScriptableObject
  Data/Relays/                    # конфигурации узлов
  Prefabs/                        # prefab роли и объекты уровня
  Tests/EditMode,Tests/PlayMode   # тесты правил и интеграции
```

Подкаталоги добавлять только при реальной нужде. Новые `.asmdef` для независимых тестовых C# модулей — по доказанной пользе, иначе сохранить существующую сборку `SectorLab`. Находящиеся в сцене `GameObject`/GUID сохранять при миграции.

## Нежелательные архитектурные ходы

- Полная перестройка на ECS/DOTS и интерфейс для каждого класса.
- Размещение бизнес-правил внутри UI, Input или `Update` каждого юнита.
- `async void` для операций матча без явной обработки исключения и токена.
- Глобальный сервис локатор как замена DI.
- Постоянный `Instantiate`/`Destroy` без учёта Addressables.
- Сложное паттерновое дерево AI вместо простого выбора команд.
