# 08. Git: подлинная, объяснимая история и безопасная автономность

## Полномочия

**Разрешено:** читать/изменять файлы проекта, тестировать, устанавливать нужные UPM пакеты, создавать короткие локальные ветки при необходимости, `git add` выборочных файлов/hunks, **локальный** `git commit` для проверенной функциональности. **Не разрешено без отдельного согласия:** push и особенно force push, rebase опубликованных коммитов, `reset --hard`, `git clean -fdx`, удаление несохранённых файлов, переписывание всей существующей истории «под идеальный сценарий».

## До первого коммита

1. `git status --short --branch`; `git log --oneline -n 15`; `git diff --stat`, `git diff --check`; `git lfs version`, `git lfs status`; сохранить снимок/патч текущих изменений в место вне репозитория (не допускать потерю untracked/binary).
2. Не считать изображения изменёнными только из-за git-lfs pointer против реального PNG. `git lfs pull` лишь при наличии надёжного доступа к remote и разрешения; не заменять содержимое неизвестными бинарниками.
3. Разобрать конфликтующие ранее подготовленные исправления: `UnitAttack` + тесты; `UnitMovement` + тесты; `UnitCommander` + тесты; документы отдельно. Для общих файлов использовать `git add -p`/маленькие промежуточные изменения **по реально существующим hunks**. Если невозможен осмысленный split — допускается один честный связанный коммит, а не ложные искусственные промежуточные версии.
4. Подтвердить состояние `packages-lock.json`, `.meta` GUID, assets, scenes и Build Profile.

## Единица коммита

**Одна небольшая завершённая логическая правка, проверенная в доступной среде.** Не дробить так, чтобы промежуточное состояние заведомо не компилировалось, только ради «красоты». Не вставлять постфактум вымышленные bugfix-коммиты и не менять автора/дату для имитации ручной разработки. AI-участие не скрывать.

Примеры типов:

```
fix: block attacks behind arena geometry
fix: recover from partial navigation paths
test: cover contested relay capture
feat: add relay ownership state
feat: accrue control points for owned relays
feat: add deterministic enemy objective selection
chore: install VContainer package
feat: configure match lifetime scope
chore: install Addressables package
chore: install UniTask package
feat: load unit prefabs through Addressables
feat: cancel respawn when match restarts
feat: add mobile camera gestures
test: verify restart releases spawned units
docs: explain match service lifetimes
```

## Перед каждым локальным коммитом

```
git status --short
git diff --check
git diff --stat
git add -- <явные-пути>
git diff --cached --stat
git diff --cached
git commit -m "type: specific change"
```

- Не использовать `git add .` вслепую, не коммитить `Library/`, `Temp/`, `Logs/`, `Builds/`, IDE кэш, архивы, секреты, credentials, keystore.
- Изменение `Main.unity`/Prefab проверять на случайные инспекторные побочные изменения, GUID, ссылочные ошибки. `.meta` хранить вместе с ассетом, не генерировать новые GUID для существующих объектов.
- Каждый зелёный коммит содержит понятные изменения и ограниченный набор релевантных файлов. Документировать проверку (например, `EditMode 14 passed`, не выдумывать число).
- При сломанном тесте/компиляции — исправить **до** коммита, если нет причины временно зафиксировать явно помеченный технический эксперимент в отдельной ветке. `main` должен оставаться играбельным.

## Что считать «хорошей историей»

Проверяющий может открыть старый коммит, понять добавленную возможность, увидеть связанные тесты, затем следующий реальный рефакторинг/фикс, не встретить гигантскую внезапную миграцию всех скриптов. История не обязана быть абсолютно линейной или состоять из одной фичи на коммит любой ценой.

## Короткие ветки и публикация

Работать в `main` допустимо после baseline с проверками. Альтернатива — ветка `feat/relay-v1`, короткие локальные слияния в `main` без переписывания remote истории. Агент выбирает вариант после осмотра актуальной конфигурации Git; решение отражает в журнале. Публикация на GitHub через `git push` или оформление публичного релиза — **отдельный запрашиваемый шаг** после финального аудита.

## Журнал для будущего изучения

`IMPLEMENTATION_STATUS.md`: milestone, task IDs, коммит SHA, файлы, что изменилось, почему, реальные команды проверок, остающиеся риски, 2–3 вопроса для будущего самостоятельного изучения. Не составлять искусственный «дневник моих размышлений» от лица пользователя.
