# Архитектура и технические решения

## Архитектура растёт вместе с игрой

- В R0 преимущественно сцена и Unity Editor; никакой «архитектурной платформы».
- На R1 достаточно одного небольшого компонента перемещения. Отдельный ввод появляется только при появлении ввода.
- Если позже команда может приходить и от игрока, и от ИИ, имеет смысл выделить границу приём/исполнение команды. **Не создавать такую систему заранее.**
- Начальные решения разрешено упрощать; важно честно фиксировать, почему затем пришлось поменять подход.

## Принципы

| Принцип | Практическая трактовка |
| --- | --- |
| KISS | Предпочитать краткое, понятное, проверяемое решение |
| YAGNI | Не реализовывать неподтверждённые будущие требования |
| Separation of Concerns / SRP | Разделять ввод, перемещение, бой, показ только при росте обязанностей |
| DRY | Не дублировать уже известные игровые правила, не создавать абстракцию ради случайно похожих строк |
| Composition over Inheritance | Для Unity обычно удобны небольшие совместимые компоненты, а не глубокая иерархия |
| Эволюционная архитектура | Рефакторинг — нормальная итерация, основанная на проблеме |

## Введение технологий без «галочек»

| Технология | Реальная задача/триггер | Что важно понять |
| --- | --- | --- |
| Unity Input System | Мышь и касания, разная схема управления | Действия, устройства, взаимодействие с UI |
| Prefab | Повторное создание юнитов | Связь шаблона и экземпляров |
| ScriptableObject | Несколько конфигураций юнитов/оружия | Настройки vs состояние экземпляра |
| Unit Tests | Расчёт урона, здоровья, правил победы | Изоляция детерминированных правил |
| UniTask | Реальная асинхронная загрузка, ожидание, отмена | CancellationToken, жизненный цикл, обработка ошибок |
| VContainer | Нетривиальные зависимости между игровыми сервисами | Регистрация, жизненные циклы, точка композиции |
| Addressables | Управляемая загрузка и выгрузка ресурсов | Время жизни handles, освобождение ресурсов |
| Пулы | Частые снаряды/эффекты | Повторное использование, сброс состояния |
| Профилирование | Проблемы кадров/памяти или замеры масштаба | Замеры на целевой платформе |

Конкретные версии сторонних пакетов не фиксируем до проверки установленного редактора, совместимости и реальной задачи.

## Когда стоит сделать spike

Отдельный небольшой **эксперимент** уместен, когда невозможно выбрать между вариантами без кода: прямое движение/физика/NavMesh; uGUI/UI Toolkit; выбор системы ввода; схема Addressables. Для spike сформулируй вопрос, ограничь объём, запиши вывод; код разрешено выбросить.

## Что тестировать

- Чистые расчёты и правила — по возможности C# классы и модульные тесты.
- Камеру/ввод/визуальную отдачу — в Unity вручную и на телефоне.
- Периодически проверять скорость кадров/сборку, но не вводить ECS/DOTS без измеримой потребности.

## Жизненный цикл сцен и объектов

В ходе развития стоит отдельно изучить: `Awake`, `OnEnable`, `Start`, `Update`, `FixedUpdate`, `OnDisable`, `OnDestroy`; в R0 заранее не строить менеджер жизненного цикла. Документировать важные предположения на примерах из конкретного кода.
