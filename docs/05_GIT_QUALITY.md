# Git и качество изменений

## Зачем нужна история коммитов

История должна отражать **настоящую последовательность разработки и понимания**: первоначальный вариант, обнаруженную проблему, исправление и разумный рефакторинг. Ошибки в прошлых коммитах — нормальны; не переписывать историю ради видимости идеального процесса.

## Рекомендованный режим

- Для одиночного прототипа — одна основная ветка `main`, короткоживущие ветки только при необходимости.
- **Атомарный коммит:** одно осмысленное изменение, которое можно проверить. Не требуется отдельный коммит на каждый щелчок.
- Не смешивать новую механику с большим форматированием и несвязанным рефакторингом.
- Коммит делать после запуска/проверки, без массовых промежуточных изменений.
- Агент не делает `git commit`, `rebase`, `reset --hard`, `push --force` без явного запроса пользователя.

## Сообщения коммитов (вариант Conventional Commits)

```text
chore: initialize Unity project
chore: add Unity gitignore
feat: add ground plane
feat: configure top-down camera
feat: add first unit
feat: implement simple unit movement
fix: stop unit at destination
refactor: separate player input from movement
refactor: simplify unit configuration
test: cover health boundaries
docs: record movement approach
```

Не обязательно следовать названиям дословно; коммит должен отражать реальный объём правок.

## Что держать в Git

Типовой Unity-проект: `Assets/` вместе с `.meta`, `Packages/`, `ProjectSettings/`, документацию, файлы настроек инструментов при необходимости. Не коммитить `Library/`, `Temp/`, `Obj/`, `Logs/`, локальные кэши, билды и секреты. Использовать проверенный Unity `.gitignore`; **не перезаписывать уже имеющийся без сравнения**.

## Минимальная проверка перед коммитом

1. `git diff --check` не показывает проблем с пробелами/концами строк (где применимо).
2. `git diff --stat` и `git diff` понятны пользователю, нет случайных файлов.
3. Unity открывается без ошибок компиляции (если шаг содержит Unity-изменения).
4. Функция работает согласно условиям готовности; известные ограничения записаны.
5. `git status` показывает только ожидаемые изменения.

Примеры команд в PowerShell:

```powershell
git status --short
git diff --check
git diff --stat
git diff
git add -- Assets/_Project/Scenes/Main.unity Assets/_Project/Scenes/Main.unity.meta
git diff --cached --stat
git commit -m "feat: add ground plane"
```

**Пример `git add` требует заменить пути реальными!** Unity-сцена может менять и другие метаданные; агент проверяет фактический diff и не предлагает бездумный `git add .`.

## Проверка на Android

Для мобильного прототипа проверка на реальном устройстве — важная цель с R0/R1. Если устройство/SDK недоступны, поставить пометку `не проверено`, не изображать успешную сборку.

## Когда писать тесты

TDD или тесты по факту — для устойчивых, отделимых игровых правил (здоровье, урон, победа, расчёт очков). Для разметки арены и света важнее ручной просмотр. После рефакторинга — регрессионная проверка.
