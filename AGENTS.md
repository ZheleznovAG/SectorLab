# AGENTS.md — SectorLab (автономная реализация v1.0)

## Новый режим — явное изменение прежних указаний

Пользователь поручает агенту **самостоятельно реализовать законченную v1.0** на базе текущего Unity-проекта, провести доступные проверки, поддерживать документацию и делать **настоящие локальные Git-коммиты**. Ранее действовавший режим «пользователь вручную делает каждую микроитерацию, агент не коммитит» для работ в `docs/agent_execution/` **заменён**. Старые документы сохраняют ценность как история решений, но не блокируют данное поручение. После завершения пользователь будет изучать код по результатам и коммитам.

## Обязательные действия в начале

1. Проверить `git status --porcelain=v1`, `git log -10`, текущую ветку, remote, `.gitattributes`, Git LFS, проект Unity, `manifest.json`, `packages-lock.json`, компиляцию и тесты (когда среда доступна).
2. Не считать приложенный архив автоматически актуальнее настоящего рабочего каталога. Если HEAD или рабочее дерево отличаются, задокументировать изменения в `docs/agent_execution/IMPLEMENTATION_STATUS.md` и применить правила разрешения конфликтов из `08_GIT_AND_AUTOMATION.md`.
3. Сохранить/зафиксировать текущие незакоммиченные правки без потери данных. Не выполнять `reset --hard`, `clean -fdx`, force push, разрушительное удаление или подмену истории.
4. Прочитать `README_START.md` и документы `02_GAME_DESIGN`, `03_REQUIREMENTS`, `06_DELIVERY_PLAN`, `09_ACCEPTANCE`.

## Режим работы

- Выполнять задачи последовательно по зависимостям и проверкам; одну независимую законченную правку (или очень маленькую связанную группу) за коммит. Можно работать автономно несколько задач подряд, **но каждый коммит должен соответствовать настоящим сделанным и проверенным изменениям**.
- Агент **может** создавать, изменять и удалять релевантные файлы Unity и docs, устанавливать требуемые пакеты, запускать редактор, тесты и сборки, выполнять локальные `git add <явные пути>` / `git commit`. Каждый такой шаг отражать в статусе.
- **Нельзя** самостоятельно делать `git push`/публиковать APK/создавать релиз в публичном репозитории без отдельного разрешения; нельзя покупать сервисы, загружать закрытые ассеты или заменять существующую лицензию проекта без проверки.
- Если Unity/Android-устройство отсутствуют: максимально завершить доступные задачи, отметить проверки `BLOCKED`, не выдавать их за PASS. Не подделывать выводы тестов, даты, скриншоты или коммиты.
- Работать поверх существующих `Main.unity`, NavMesh, `Unit`, `UnitAttack`, `UnitMovement`, `UnitCommander`, тестов и префабов. Рефакторить обоснованно, а не переписывать с нуля.
- Предпочитать русский язык объяснений/документации, общепринятые английские названия API оставить без перевода.

## Технические ограничения

- Не вводить ECS/DOTS, мультиплеер, сетевой сервис, локальную LLM, собственный контейнер DI, общий EventBus, ненужные generic-абстракции и масштабируемую RTS-инфраструктуру.
- VContainer внедрять на уровне composition root для служб матча; UniTask — только для настоящих асинхронных сценариев с отменой; Addressables — для локально поставляемых префабов/ресурсов со строгим владением handle.
- Вопросы жизненного цикла/отмены при перезапуске, смерти юнита и ошибке загрузки — обязательные тестируемые сценарии.
- Доработки игровой механики не смешивать с глобальным переформатированием или переписыванием статических `.meta`/`.unity` без необходимости.

## Качество каждой задачи

1. Требование с ID и наблюдаемая цель.
2. Изменённые файлы и объяснение проектного решения.
3. Компиляция (если возможно), подходящие EditMode/PlayMode-тесты и ручная проверка Play Mode.
4. `git diff --check`, обзор `git diff --cached`, проверка случайных файлов и LFS.
5. Локальный коммит только после проверки; если проверка недоступна — отдельный `BLOCKED` в журнале и коммит только для явно безопасной части с честной пометкой.
6. Обновление `IMPLEMENTATION_STATUS.md` и реестра требований/решений.

## Отчётность и остановка

После milestone сообщать: реализовано, коммиты, PASS/FAIL/BLOCKED, известные проблемы, следующий milestone. Не завершать работу отчётом «всё готово», пока `09_ACCEPTANCE.md` не выполнен. Если игровое требование конфликтует с техническим, предпочесть функционирующую и понятную игру; зафиксировать ADR. Не дописывать план бесконечно, держать scope v1.0.
